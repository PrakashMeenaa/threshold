# Architecture

## RLS on `clinics`

`clinics` carries a self-referential RLS policy (`id = current_setting('app.current_clinic_id', true)::uuid`) rather than being left outside RLS, so that no table in the schema is exempt from tenant scoping at the database layer. The one exception is a single audited path: `resolve_clinic_by_phone(phone_number_id text) RETURNS uuid`, which lets the webhook handler resolve which clinic a message belongs to before any `app.current_clinic_id` session context exists. It returns only `clinic_id`, never the full row.

The function is `SECURITY DEFINER`, owned by a dedicated role, `threshold_rls_bypass` (`NOLOGIN`, `NOSUPERUSER`, `BYPASSRLS`) — not by the bootstrap role. `threshold_rls_bypass` exists solely to own this function; nothing ever connects as it. It holds a column-scoped grant, `SELECT (id, whatsapp_phone_number_id) ON clinics`, not the whole row, and `EXECUTE` on the function is revoked from `PUBLIC` and granted only to `threshold_api_user`. `threshold_app` additionally holds membership in `threshold_rls_bypass` (not login rights — just the membership Postgres requires to run `ALTER FUNCTION ... OWNER TO`).

This design is deliberate: it would be easy to let the function's `SECURITY DEFINER` bypass ride on `threshold_app` being a Postgres superuser, since that's true by default in local Docker (`initdb`'s user is always superuser, and superusers bypass RLS unconditionally, independent of `FORCE ROW LEVEL SECURITY`). But that's an accident of the dev environment, not a designed exception — no managed Postgres provider (RDS, Cloud SQL, Supabase) hands out true superuser to its admin role. Had the function stayed owned by `threshold_app`, it would silently start returning nothing for every phone number the moment `threshold_app` lost superuser status, breaking webhook routing for every clinic with nothing pointing at RLS as the cause. Routing the bypass through `threshold_rls_bypass` instead makes it an explicit, minimally-scoped, auditable grant that behaves identically regardless of `threshold_app`'s privilege level.

Example call: `SELECT resolve_clinic_by_phone($1) AS clinic_id;`

Because the `clinics` policy has no `FOR` clause, it also governs `INSERT`, and `WITH CHECK` is evaluated after column defaults are computed — so relying on `clinics.id`'s `gen_random_uuid()` default can never satisfy the check (the server-generated value can't be known in advance to match a session variable set beforehand). The default stays in the schema, but every real insert path must explicitly supply `id`, matching the session var set just before. In practice, creating a new clinic requires:

1. Generate the clinic's UUID application-side (not the column default).
2. `SET LOCAL app.current_clinic_id` to that same UUID.
3. Insert the `clinics` row, explicitly supplying `id`.
4. Only then proceed to insert `departments`, `doctors`, etc. for that clinic, as before.

This ordering is a hard requirement for the Step 1.3 seed script, not just for `clinics` — every dependent insert for a new clinic must happen after steps 1–3.

## Webhook Tenant Routing and Idempotency (Step 2.2)

`POST /webhook` has no clinic context until the payload itself is parsed — `phone_number_id` is the only signal identifying which clinic a message belongs to, and it only exists inside the (HMAC-verified) request body. The `get_webhook_context` dependency resolves this by acquiring one pooled connection, opening a transaction, calling `resolve_clinic_by_phone` (the same `SECURITY DEFINER` function documented above) to get `clinic_id` without needing RLS context first, then issuing `SET LOCAL app.current_clinic_id` via `set_config` on that same connection before yielding it to the route handler. The transaction stays open for the whole request specifically so `app.current_clinic_id` (transaction-scoped) applies consistently to every query the handler makes — including the idempotency check — before committing (or rolling back on error) and releasing the connection back to the pool. Using two separate connection checkouts here would have been a bug: `SET LOCAL` on one connection has no effect on a different connection pulled from the pool for a later query.

Idempotent redelivery is enforced by a dedicated `processed_webhooks` table (0015), keyed on `(clinic_id, payload_hash)` where `payload_hash` is a SHA-256 over the four validated payload fields (not the raw JSON bytes, since a legitimate redelivery isn't guaranteed to be byte-identical). The check is a single `INSERT ... ON CONFLICT (clinic_id, payload_hash) DO NOTHING RETURNING id` rather than a `SELECT` followed by an `INSERT` — two concurrent deliveries of the same duplicate could both pass a `SELECT`-based check before either row exists, double-processing the message. The atomic form makes the database itself the source of truth for "have we seen this," consistent with this project's rule that state transitions live in testable code paths, not best-effort application logic. Like `consents` and `gate_log`, `processed_webhooks` only grants `SELECT`/`INSERT` to `threshold_api_user` — an idempotency record should never be updated or deleted once written.

## Request Body Size Limiting

`MaxBodySizeMiddleware` caps request bodies at `MAX_BODY_BYTES` by counting bytes as they arrive in the ASGI `receive()` callable and rejecting with 413 once the cap is exceeded — deliberately implemented as ASGI middleware rather than a FastAPI dependency. A `Depends()`-based size check runs too late to matter: FastAPI resolves the body into its Pydantic model as part of handling the route, and by the time any dependency (decorator-level or not) executes, the full body has typically already been read into memory by FastAPI's own internal body handling. Only middleware wrapping the raw ASGI `receive()` sits ahead of that read. Any future endpoint accepting a body should rely on this same middleware (already applied at the `app` level, not per-route) rather than re-deriving a per-dependency size check.

## Onboarding Agent (Phase 4)

`apps/api/onboarding_agent.py` implements the name → language → consent → department state machine. The LLM's role is strictly extraction: `SlotExtractor` (a `Protocol`, with `AnthropicSlotExtractor` as the real implementation) turns free text into a strictly-typed Pydantic result via `client.messages.parse(output_format=...)`, and every extracted value is validated in plain Python before it's trusted — `_match_option` does a case/whitespace-normalized lookup against the clinic's actual configured `languages` or live `departments` rows, so the model can only ever select from a real, closed set, never introduce a value that doesn't exist. This mirrors the same "LLM suggests, Python decides" boundary the safety gate already enforces.

State lives in `conversation_state` (`agent='onboarding'`), read via `load_onboarding_state`, which does `INSERT ... ON CONFLICT DO NOTHING` before `SELECT ... FOR UPDATE` — the insert-first step matters because `FOR UPDATE` can't lock a row that doesn't exist yet, so without it the very first message from a new patient would still race under concurrent delivery. The lock is taken before `advance_onboarding` runs and held until the request's transaction commits, serializing any second concurrent turn from the same patient behind the first.

Consent is recorded with the clinic's exact `consent_text` (sourced from `clinics/*.yaml`, loaded once at startup into a `phone_number_id`-keyed `ClinicRuntimeConfig` map — the same YAML-only, non-DB-persisted treatment as `greeting`) plus `granted_at`'s timestamp, satisfying the "exact text shown" constraint literally. Repeated identical answers at `awaiting_consent`/`awaiting_department` are bounded by `MAX_UNCLEAR_ATTEMPTS` and, for decline specifically, deduplicated — only the first decline in a streak inserts a `consents` row, since the audit log is supposed to record decisions, not repeated re-statements of the same one.

The Anthropic call itself runs inside the same DB transaction that holds the `FOR UPDATE` lock and one of the connection pool's limited slots, so it carries an explicit 20-second timeout (`client.with_options(timeout=...)`) rather than the SDK's 10-minute default — a slow call there doesn't just delay one patient's turn, it holds a shared resource every other webhook request depends on. A failed or timed-out extraction raises `ExtractionFailure`, caught in `advance_onboarding` and mapped to a generic retry reply, never advancing state or leaking the underlying error.

## Safety Gate (Step 3.1)

`apps/api/safety_gate.py` is a pure function, `evaluate(text: str) -> GateResult`, with no I/O, no DB access, and no `async` — deliberate, so it stays independently unit-testable and structurally cannot become a place where an LLM's output influences control flow, per `CLAUDE.md`'s rule that LLM calls are read-only with respect to control flow. It runs inside `receive_webhook` immediately after the idempotency check, before anything resembling agent dispatch exists yet — the seam Phase 4/5 build real agent logic onto for the non-triggered path.

Six categories: five treated as emergencies (`chest_pain_cardiac`, `breathing_distress`, `stroke_symptoms`, `severe_bleeding_trauma`, `self_harm_crisis`) and one, `medical_advice_request`, that isn't an emergency but also isn't something the eventual booking/onboarding agents should attempt to answer. Emergency categories are checked first; a message matching both an emergency pattern and the medical-advice pattern gets the emergency reply. Detection is broad substring/regex matching against ambiguous, colloquial phrasing rather than exact clinical terminology — false positives are the accepted failure mode, false negatives are not.

On a trigger, `log_gate_event` writes exactly `{clinic_id, category, action}` to `gate_log` — no phone number, no message text, matching the Phase 3 constraint directly. `action` is `"escalated"` for the five emergency categories and `"deflected"` for medical advice, derived by `action_for_category` so the category→action mapping lives in exactly one place. Migration 0016 adds `CHECK` constraints on both `gate_log` columns, matching the pattern already used for `availability_slots.status`/`appointments.status` elsewhere in the schema.

Coverage includes a first-pass Hindi/Hinglish (romanized Hindi) pattern set per category, since `clinics/sunrise.yaml` declares `languages: [en, hi]` — an English-only gate would provide zero safety coverage for Hindi-speaking patients at that clinic despite it explicitly advertising Hindi support. These patterns are a first pass that has already been through one round of correction; they should not be treated as clinically or linguistically exhaustive without further native-speaker review, particularly for `self_harm_crisis`, where a false negative is the most costly failure mode in the whole module.

**Per-clinic escalation text is composed, not read inside the gate.** Each `clinics/*.yaml` carries an `escalation_rule` string, loaded into `ClinicRuntimeConfig.escalation_rule` alongside `greeting`/`consent_text`. `safety_gate.compose_reply(base_reply, escalation_rule)` is a second pure function (no I/O, same file as `evaluate`) that appends the clinic's text after the hardcoded `EMERGENCY_REPLY`/`MEDICAL_ADVICE_REPLY`, or returns the base reply unchanged if the rule is missing, empty, or whitespace-only. `evaluate(text: str) -> GateResult` itself takes no clinic argument and is unchanged by this — the gate's detection logic stays independent of any per-clinic configuration, and the composition step is a separate concern the caller applies afterward.

Ordering in `receive_webhook` matters here and is deliberate: the gate is evaluated and can return a reply *before* clinic config is resolved or validated, exactly as it was prior to this feature. The clinic-config lookup for the escalation text happens only inside the already-triggered branch, using `.get()` rather than a hard requirement — if it comes back `None`, `compose_reply` just falls back to the safe hardcoded text. A missing or malformed clinic YAML can degrade the *personalization* of an emergency reply; it cannot prevent the gate from replying with the core safety instruction at all. This is the same "the gate must not depend on anything that can fail" posture the module has had since Phase 3, extended to cover a feature added after that phase closed.

## Appointment Agent (Phase 5)

`apps/api/appointment_agent.py` handles book/reschedule/cancel once onboarding's own `conversation_state` reaches `complete` — `main.py` checks that step before dispatching, replacing what used to be a canned placeholder. It reuses Phase 4's exact pattern: a `Protocol` extractor with Pydantic structured output via `client.messages.parse`, `FOR UPDATE` locking on `conversation_state` for the same per-patient turn-serialization guarantee, and the same `MAX_UNCLEAR_ATTEMPTS`-bounded retry discipline (imported directly from `onboarding_agent`, not reimplemented, so the two stay in sync).

One dependency this phase needed that Phase 4 hadn't provided: which department a patient wants. That previously only lived inside onboarding's own private `conversation_state` JSONB — reaching into another agent's internal state shape from here would be a layering violation, so `patients.department_id` (composite-FK'd to `departments`, same clinic-consistency pattern as 0011) was added, and `onboarding_agent.py` was updated to write it alongside its own state when the department step completes.

**Natural-language date resolution** is deliberately not hand-rolled in Python. The LLM is given the current UTC timestamp as explicit context and asked to resolve phrases like "next Tuesday afternoon" into a structured ISO datetime — but Python never trusts the *semantics* of that resolution, only validates the *result* (parseable, not in the past) and then uses it purely as a search target against real `availability_slots`, returning the 3 closest actual matches rather than assuming the LLM's date is itself bookable. The "LLM suggests, Python decides" boundary holds even though, unlike onboarding's closed-vocabulary matches, there's no fixed set to check the LLM's answer against here.

**Concurrency (the actual PLAN.md requirement) is enforced twice.** `book_slot` does `SELECT status FROM availability_slots ... FOR UPDATE` before checking it's `'available'`, serializing concurrent booking attempts for the same slot at the database level rather than an application check-then-write. Migration 0019 adds a second, physical guarantee: `CREATE UNIQUE INDEX ... ON appointments (slot_id) WHERE status = 'booked'` — even a bug in the locking logic can't produce two active bookings for one slot. `tests/test_appointment_agent.py::test_concurrent_booking_only_one_succeeds` proves the lock actually blocks a second transaction (not just that the code looks correct) using two genuinely separate connections.

**Reschedule is cancel-old-and-book-new, not an in-place update** — a fresh `appointments` row for the new booking, the old one marked `cancelled` — preserving full history rather than losing what the original booking was, consistent with this project's append-only-audit bias elsewhere (`consents`, `gate_log`). The new slot is booked *before* the old one is cancelled specifically so a lost race on the new slot never leaves the patient with neither appointment.

**Two failure modes that look similar are kept deliberately separate.** A patient giving an unparseable or ambiguous reply consumes the bounded `unclear_count` retry budget and eventually gets told a staff member can help. A patient giving a perfectly valid selection that loses a booking race to someone else does *not* consume that budget and gets a different message ("that slot was just taken") — conflating the two would tell a patient they'd been confusing when the real cause was contention that was never their fault.

Patient-facing appointment times render in the clinic's actual timezone (`clinics.timezone`, read via `fetch_clinic_timezone`) rather than raw UTC — that column existed since Phase 1 but was never populated by `seed.py` until this phase, silently defaulting to `'UTC'` the whole time.

## Clinic Dashboard (Phase 6)

`apps/dashboard` is the first code in this project outside `apps/api` — a separate Next.js app, its own runtime, its own dependency tree, but held to the same RLS/IDOR discipline as everything else. Staff login has the exact same chicken-and-egg RLS problem webhook routing had in Phase 2: `staff_users.email` is only unique *per clinic*, so a login attempt can't be scoped by `app.current_clinic_id` before it knows which clinic the email belongs to. Migration 0020 solves it identically to 0013 — `resolve_staff_by_email`, a `SECURITY DEFINER` function owned by the same `threshold_rls_bypass` role (reused, not duplicated), column-scoped grant, `EXECUTE` revoked from `PUBLIC`.

**Sessions are self-contained, HMAC-signed cookies** (`lib/session.ts`) rather than a server-side session table — deliberately built on the Web Crypto API (`crypto.subtle`) instead of Node's `crypto` module, specifically because `proxy.ts` (Next.js 16's replacement for `middleware.ts`, migrated to during this phase rather than shipping something already flagged deprecated) always runs on the Node runtime and Web Crypto works identically there, avoiding any Edge-vs-Node API-surface guesswork. The tradeoff, named rather than silently accepted: there's no way to revoke one compromised session before its 8-hour expiry, only rotate `SESSION_SECRET` to invalidate every session at once.

**Auth enforcement is centralized in `proxy.ts`**, not scattered per-page — it decodes and verifies the session cookie for every `/dashboard/:path*` and `/api/:path*` request before any route handler runs, redirecting page requests to `/login` and returning a bare 401 for API requests. Individual pages/routes still call `requireSession()`/`getSession()` themselves too, on purpose — same "don't trust one layer" posture as RLS-plus-explicit-`clinic_id`-filtering elsewhere in this project, not redundancy for its own sake.

**IDOR protection is the literal PLAN.md requirement, not an afterthought.** `fetchPatientById`/`fetchAppointmentById` filter `WHERE id = $1 AND clinic_id = $2` using the *session's* `clinicId` — never trusting RLS alone to keep a request scoped. `tests/tenant-isolation.test.ts` proves this against a real Postgres connection: a Sunrise-scoped lookup of a City Dental ID returns `null`, not the row RLS would have hidden anyway if the explicit filter weren't there.

**Server Actions' built-in CSRF protection isn't trustworthy enough to rely on alone.** A documented CVE (opaque/null-origin requests from sandboxed iframes bypassing Next.js's Origin/Host check) and an acknowledged structural gap (a request with no Origin header at all is let through with only a warning) mean `loginAction`/`logoutAction` both call `verifySameOrigin()` explicitly before doing anything else — a stricter, auditable check that hard-rejects a missing Origin rather than warning and continuing.

**Patients who explicitly declined onboarding consent get redacted server-side**, not just hidden in the UI — `toPatientRow` replaces `full_name`/`preferred_language`/`department_name` with a generic "Declined contact" marker *before* the data ever leaves the query function, so a declined patient's real name never reaches the browser at all, let alone gets displayed. This only needed handling on the patients view: a patient who declines never gets `department_id` set during onboarding, so they can never reach the appointment agent, meaning no declined patient can ever have an appointment row to redact on that view.

## Evals + Replay Harness (Phase 7)

`evals/run_evals.py` replays 12 golden conversations against the real state-machine code, entirely offline: the 5 seeded in the assignment brief (happy-path English booking, emergency-gate routing, medical-advice-gate routing, abandon/resume, relative-date booking) plus 7 authored for this project — 4 explicit failure cases (exhausted consent retries, cross-tenant department rejection, an out-of-bounds requested time, a lost booking race) and 3 edge cases (explicit consent decline, an ambiguous multi-appointment cancel, Hindi-language onboarding).

`MockSlotExtractor`/`MockAppointmentExtractor` stand in for `AnthropicSlotExtractor`/`AnthropicAppointmentExtractor`, replaying a per-case queue of pre-authored structured extraction results (`evals/cases.json`) instead of calling the Anthropic API — the same "LLM suggests, Python decides" boundary the production code already enforces, applied to testing: the harness proves `advance_onboarding`/`advance_appointment` act correctly on a given extraction, not that an LLM can extract correctly. The database is not mocked, though. Each case runs against the real local Postgres instance inside its own transaction, always rolled back, so the harness exercises the actual `FOR UPDATE` locking, RLS session variable, and schema constraints (`consents`, `conversation_state`, the partial unique index on `appointments`) rather than a stand-in that would pass regardless of whether persistence actually works. Rollback isolation is verified, not assumed — `patients`/`appointments`/`availability_slots`/`consents` row counts are identical before and after a full run.

Every expected value in `cases.json` — next step, reply text, what got persisted — is traced against the corresponding production code path rather than restated from a one-line case description. Case 12 (booking race loss), for example, asserts `unclear_count` stays 0 specifically because `_handle_slot_selection`'s race-loss branch returns before ever calling `save_appointment_state`, not merely because the number happens to read 0 today. Reply text that depends on clinic-specific YAML content (`consent_text`, the language/department prompt lists) is checked against the same `language_question()`/`department_question()`/`ClinicRuntimeConfig.consent_text` the production code itself calls, computed at harness run time rather than hardcoded into the case file, so the eval can't silently drift from `clinics/*.yaml`.

`_run_case` wraps both the gate-check path and the per-case DB transaction in `try/except Exception`, converting any unexpected exception into a one-line failure entry on that case's own `CaseOutcome` rather than letting it propagate. An earlier version only wrapped the transaction in `try/finally`, so a single case that crashed outright (rather than failing a normal assertion) would abort the entire report before it printed — discarding the pass/fail status of every case that had already succeeded. Verified against a deliberately-broken case built to trigger exactly that failure mode, not just reasoned about.

## Docker Compose, CI, and Deploy (Phase 8)

`docker-compose.yml` defines three services: `db` (Postgres, unchanged since Phase 0, now with a `pg_isready` healthcheck other services key their startup ordering on), `api` (`apps/api/Dockerfile`), and `dashboard` (`apps/dashboard/Dockerfile`). Both application services read secrets from a single `.env` via `env_file`, with `PGHOST`/`PGPORT` overridden to the Compose network's `db:5432` — the API and dashboard's own `load_db_config()`/`lib/db.ts` default to `localhost:5433` for host-run development, so no code change was needed, only compose-level environment overrides, exactly as anticipated back in Phase 2's original note about this exact seam.

`apps/api/Dockerfile` installs dependencies with `uv sync` in two passes — once against only `pyproject.toml`/`uv.lock` (`--no-install-project`, for Docker layer caching independent of source changes), once after the actual source is copied in — both with `--frozen --no-dev`, so the image never resolves against the network at build time beyond the initial dependency fetch, and never includes test-only dependencies. The container's `CMD` is `uv run --no-sync uvicorn ...`, not the more obvious `uv run uvicorn ...`: `uv run` performs an implicit sync-and-verify against the lockfile before running anything, and without `--no-sync` this happens on every container start — with no matching `--no-dev` on that implicit check, it would additionally try to install the dev dependency group over the network at runtime, turning a finished image into one still dependent on PyPI availability just to start.

`apps/dashboard/Dockerfile` is a three-stage build (`deps`, `builder`, `runner`) producing a Next.js `output: "standalone"` image — only the standalone server bundle, static assets, and `public/` ship in the final stage, not the full `node_modules` tree. The `builder` stage sets two placeholder environment variables (`THRESHOLD_API_PASSWORD`, `SESSION_SECRET`) purely for the duration of `npm run build`, real values injected only at container runtime via `env_file`. These are not optional: `next build`'s page-data collection step actually executes route modules to determine static-vs-dynamic classification, and `/api/patients/[id]` imports `lib/db.ts` at module scope — without a placeholder present, the build fails outright rather than merely warning.

`.github/workflows/ci.yml` runs three jobs on every push and pull request: `gitleaks` (full-history secret scan, matching the local pre-commit hook), `api-tests` (migrate, seed, the full `pytest` suite — including the RLS/tenant-isolation proof run against the unprivileged runtime role, not the bootstrap role — then the offline eval harness), and `dashboard-tests` (migrate, seed, `npm run build`, then `npm run test`). Each job provisions its own ephemeral `postgres:16` service container rather than sharing state across jobs. Running `next build` in CI, not just `vitest`, is deliberate: it's the same check that caught a real strict-TypeScript bug during Phase 6 that neither Vitest nor ESLint flagged.

The Phase 8 acceptance bar — a fresh clone reaching a working `simulate.sh` conversation in under 15 minutes — was measured directly rather than assumed: a clean copy of the tree, with every local container/volume/network torn down first, taken through the README's own documented commands verbatim (generate `.env`, bring up Postgres, migrate, seed, build and start `api`/`dashboard`, run `simulate.sh`) completed in 21 seconds end to end (excluding first-time base-image pulls, which depend on network speed rather than anything in this repo).
